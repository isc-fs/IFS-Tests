# MingoQuiz red-team report (functional, no security)

- **Target:** `isc-fs/IFS-Tests`, branch `dev`, commit `0fe0605` (2026-09-24).
- **Scope:** functional correctness, game rules, data integrity, reliability, operations, UX, docs vs reality. Security was out of scope and not tested.
- **Status:** report only. Nothing in the repository was changed; every agent finished with `git status` clean.

---

## 1. Verdict

MingoQuiz is in better shape than most projects at this stage:
- All CI checks are green: 825 Python tests, 142 web tests, lint and types.
- Coverage is 94 % overall and 98 % for the core layers.
- Onboarding works literally as documented.
- Every worked example in `game-rules.md` reproduces to the cent.
- Randomised multi-season simulations found no accounting drift between answers, XP, LP, streaks and leaderboards.
- Live-quiz events fan out correctly across two workers.
- Migrations are clean in both directions.

The problems sit where the tests don't look: operations that run rarely, boundaries in time, real-world data, and scale.

1. **Recovery is broken exactly when you need it.** Restoring a dump older than the current schema fails part-way. Prod stays down with a mixed database (OPS-01). The deploy smoke test can't see a dead database connection (OPS-03).
2. **The once-a-season bank refresh damages history.** Any upstream edit to a choice question rebuilds its options with new IDs. Finished mock runs and daily reviews that contain it then return 400 forever (BANK-01). A solution added upstream wipes reviewer corrections (BANK-07), and deletions upstream never propagate (BANK-08).
3. **Some real questions are graded wrong.**
   - Integer pairs such as `118, 122` are parsed as `118.122` (BANK-03).
   - Questions FS-Quiz marks as removed or wrong are still drawn as dailies (BANK-02).
   - Units and `%` make a right answer wrong instead of being refused (BANK-04).
   - The 0.1 % tolerance accepts wrong exact answers (BANK-05).
4. **A live quiz at a full team meeting doesn't hold up.** With "Seat by sub-department", 12 of 22 tables never get a question (LIVE-01). At 80 phones, the production limits (1 CPU, 2 workers) saturate and screens lag 3–10 s (LIVE-02).
5. **Midnight and the 03:00 job cause a cluster of edge bugs.**
   - A daily started just before midnight vanishes and is charged as late (PLAY-03).
   - A streak freeze only applies at 03:00, so early-morning play loses the streak bonus (PLAY-04).
   - Rested XP counts a played day as a day away (DOM-05).
6. **Game-integrity holes.**
   - Number hints can land inside the answer's tolerance (DOM-01).
   - A blind guess pays during a bad run (DOM-02).
   - Mock summaries count late answers as right (DOM-03).
   - An abandoned mock run blocks dailies indefinitely (PLAY-05).
7. **One front-end bug makes e2e flaky** (GATE-01). When the learning aids load, they rebuild the question card and wipe the player's answer. This failed e2e in 2 of 3 runs, in two separate agents.

8. **Performance is fine for everyday use, but degrades in two places.**
   - Steady traffic stays under 46 ms at p95. The 00:01 daily race picks exactly one question. 140 simultaneous sign-ins caused zero 503s.
   - The live quiz degrades at meeting size. Two agents measured this independently, with different scripts (LIVE-02/PERF-01).
   - The leaderboard reads every past attempt on each view. After three seasons, 60 people opening it at once see p95 ≈ 6 s (PERF-03).
   - Concurrent data exports hit the api's 512 MiB limit (PERF-04).
9. **The web app works on normal use but fails badly when a request fails.** There's no overflow at any size, axe finds nothing, and it can all be done by keyboard. But:
   - If the automatic send at zero fails, the player is stuck with no retry (UI-01).
   - Offline, the app shows nothing at all (UI-05).
   - A reviewer's correction can silently turn a range question into a text one (UI-03).

## 3. Critical and High findings

### OPS-01 — Restoring an older dump fails part-way and leaves prod down (Critical, Confirmed)
- **Where:** `deploy/restore.sh:44` (`pg_restore --clean --if-exists` under `set -e`); `docs/runbook.md:137,151,155`.
- **What happens:**
  - `--clean` only drops objects that are in the dump, so tables and functions created by newer migrations survive.
  - A surviving table with a foreign key to `users` blocks `DROP TABLE users`. `pg_restore` exits 1 ("errors ignored on restore: 6").
  - The script dies with `api` and `scheduler` already stopped.
  - `users` keeps today's rows while every other table comes from the dump.
  - `alembic_version` says the dump's revision but the schema is newer, so every later deploy of that migration fails with `DuplicateTable`.
- **Who hits it:**
  - Runbook §3 "roll back, then restore the pre-deploy dump".
  - The §4 restore drill whenever staging is a migration ahead of prod.
  - Any restore of a dump taken before a table-creating migration. It reproduced with a real 0014 dump restored onto 0016.
- **Evidence:** `ops/log-restore1.txt`.
- **Fix direction:** restore into an empty schema (drop and recreate `public` as `migrator`, re-apply the role grants), then `pg_restore --exit-on-error --single-transaction`. Take a safety dump first and always restart the app on exit. See also OPS-02, OPS-04 and OPS-14.

### OPS-03 — Deploy smoke test never touches the database (High, Confirmed)
- **Where:** `deploy/deploy.sh:71-93`; runbook "is the site up" checks at `:87,172,232,263`.
- **What happens:** redeploying with a wrong `APP_PASSWORD`, the easy slip during secret rotation:
  - The smoke test printed four `ok` lines and `deploy: done`, exit 0.
  - Both containers showed healthy, and there was no rollback.
  - Every request, login included, returned 500.
  - The scheduler logged `password authentication failed` and stayed healthy.
  - A missing SPA (`/` returns 404) also passes.
- **Evidence:** `ops/log-badpw.txt`.
- **Fix direction:** add a check that queries the database as `app_rt` (a `/readyz`) and one for `GET /`, both to the smoke test and to the runbook.

### BANK-01 — A bank reload that touches a choice question breaks its history (High, Confirmed, re-run)
- **Where:** `services/bank.py:147-157` deletes and recreates the options of a changed question; `services/questions.py:178-179` refuses option IDs that no longer exist; stored answers are re-checked in `services/mock.py:290` and `services/daily.py:291`.
- **What happens:**
  - Any change to the question's hash rebuilds its options with new IDs: a typo fix, reordered options, a solution added upstream, a new image.
  - Stored answers keep the old IDs, so a finished mock run and the daily review return `400 "Pick one of the listed answers."` for good.
  - A player who has the question open gets 400 when submitting the option on screen.
  - A change only to the text isn't flagged in "Changed upstream".
- **Why it will happen:**
  - `refresh-bank.sh` always passes `--refresh`, so upstream edits do arrive.
  - The runbook calls it "safe to repeat".
  - The reviewers' guide says past answers are never re-graded.
- **Evidence:** `bank/test_reimport_effects.py` (re-run: finished mock 400; daily review of 90001 and 90008 400; options `[1,2,3,4]` became `[24..27]` while the stored answer is `{'options': [1]}`), `test_reload_open_plays.py`, `test_reload_open_daily.py`.
- **Fix direction:** keep option rows stable, matched by FS-Quiz `answer_id` and updated in place. Never re-validate stored answers when rebuilding a summary or review.

### BANK-02 — Questions FS-Quiz marks removed or wrong, and single-option "free points", are graded and drawn as dailies (High, Confirmed / partly Plausible)
- **Where:** the quiz's `information` note is imported (`bank/normalize.py:110`, `services/bank.py:84`) and never read. `build_key` grades a single choice with one option like any other.
- **Which questions:**
  - The solution itself says "removed" or "deleted": 146 (still graded, 113.3N as the right option), 747, 841, 855, 857, 864, 923, 949.
  - Mapped from quiz notes (Plausible): 724, 723, 451, 520.
  - One option only, always right: 623, 625, 861. 887 is a range stored as a one-option single choice.
- **Impact:** 14 of these 16 were drawn as a daily in a simulated year, and no reviewer queue surfaces them.
- **Fix direction:** send "removed/deleted" notes to a review queue or exclude those questions; make choice questions with fewer than 2 options ungraded; show quiz notes to reviewers.

### BANK-03 — Integer pairs "a, b" are parsed as one decimal number (High, Confirmed, re-run)
- **Where:** `domain/keys.py:35`: `number()` strips spaces, so `"118, 122"` becomes `"118,122"`, a decimal comma. `keys.py:84` tries `number` before `numbers`.
- **What happens:**
  - Q635 `118, 122` becomes 118.122 ± 0.118. The right answer "118" is graded wrong, and so is "122".
  - Q617 `560, 30` becomes 560.3. Q675 `580000, 129` becomes 580000.129. Q452 `1, 7` becomes 1.7.
  - The UI then shows single-number hints that mislead.
- **Re-check:** `build_key('input',[{'text':'118, 122',…}])` returns `{'kind':'number','accept':[{'v':118.122,'d':3}]}`, and both 118 and 122 grade False.
- **Fix direction:** don't join digits across `", "`, and try `numbers()` first. Q635 really means "either value", which needs alternatives (BANK-06).

### LIVE-01 — Specialist routing sends a shared topic only to its first table (High, Confirmed)
- **Where:** `domain/live.py:85-87` (`owner` returns the first table that owns the topic); `services/live.py:429-440` (tables in ID order); `web/src/routes/LiveHost.tsx:350-361` (the lobby warning only lists topics nobody owns).
- **What happens:** after "Seat by sub-department":
  - `powertrain` always goes to Cooling System, `dynamics` to Braking and Steering, and so on.
  - 12 of 22 sub-department tables never get a question and earn 0 XP all session: Motor Inverter, Powertrain, Transmission, Suspension and Dynamics, Testing, Composites, Electronic Subsystems, Telemetry, Integration, Pipeline, Cost Report, Design.
  - ADR 0005's promise, questions go to "the people who know that subject best", fails for most of the team.
- **Evidence:** `live/test_meeting.py::test_specialist_routing_with_shared_topics`.
- **Fix direction:** spread a shared topic's questions across its owners, or let all owners answer and take one. At least warn in the lobby about owners that will never get a question.

### LIVE-02 / PERF-01 — A full-meeting live quiz saturates the production API (High, Confirmed by two agents independently)
- **Where:**
  - `services/live.py:489`: every proposal bumps the room-wide version.
  - `web/src/lib/live.ts:13,22-27`: every event makes every screen refetch the full state, plus a 5 s poll.
  - `deploy/compose.yaml:31`: `cpus: 1.0`.
  - ADR 0005, "Load".
- **Setup:** own stack with the production limits; 80 players, 21 tables, 30 s questions, non-captains proposing 1–3 times.
- **What happens:**
  - One state fetch costs about 25 ms of CPU. During proposals that means about 98 fetches per second against a capacity of about 40.
  - The API sits at 100 % CPU.
  - State fetch p95 is 3.4–10.3 s (max 15.7 s); answer p95 is 3.8–15 s (max 62.5 s).
  - At 40 players, p95 is 0.7 s.
  - 200 simultaneous state fetches take 3.6 s, against the ADR's "under a second".
  - Scoring stays fair, because the server timestamps each answer.
  - Plausible, not tested through Nginx: during the backlog the campus IP's in-flight requests could reach Nginx's `limit_conn 160`, and phones would get 503.
- **Independent measurement (PERF-01)**, from the perf agent's own stack: a season of data, the production limits, 20 tables seated by sub-department.
  - api CPU 85–100 %, DB about 15 %.
  - 61 screens: state fetch p95 1.55 s; a new question reaches screens p95 1.41 s late.
  - 90 screens: state fetch p95 2.58 s; a new question arrives p95 2.89 s late.
  - With heavy host load, the slowest answer took 13 s.
  - Proposals and answers are 4–9× over the documented 300 ms p95 for submits.
  - 15–19 of 20 connections sat "idle in transaction" while their threads waited for CPU. No pool timeout and no 5xx, but the margin is thin.
  - With the api on 2 CPUs, latency roughly halves (p95 1.12 s at 90 screens).
  - Integrity held: every client saw every question, and XP was granted exactly once (600/600, 690/690).
- **Also contributes:**
  - Every open stream runs UPDATE/SELECT/COMMIT once a second (`api/routes/live.py:199-209`); 60 idle streams alone use 10–15 % CPU.
  - PERF-02: the captain whose answer closes a question waits 4–13 s while XP is shared to the whole room inside that request.
- **Evidence:** `live/load_probe*.py`, `cost_probe.py`, `load_rt_80.log`; `perf/meeting.py` plus `sampler.py`.
- **Fix direction:**
  - Stop bumping the room-wide version on proposals (use a per-table channel).
  - Poll once per process instead of once per stream, or use `LISTEN/NOTIFY`.
  - Make the state view cheaper or cached.
  - Share XP after responding (PERF-02).
  - Stopgap: give the api 2 CPUs.
  - Then re-measure the ADR's claims under the deployed limits.

  - Every number in game-rules §8.1–8.3, the level table and the recalibration examples.

  - The 1 September reset through the API.
